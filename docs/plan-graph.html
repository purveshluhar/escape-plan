How to read this page

Escape Plan is a game. Each building discipline gets a token (a game piece), and each token must find a way out of the building. Five people build it in 10 hours, in three tiers. Each view below answers one question: when, how the parts connect, who owns each feature, and what the audience sees. Each view has an "In plain words" box.

Words you will see

Token
a game piece for one discipline, such as the chiller, a glass panel, a wheelchair user or the structural load. Later tiers add people, smoke, water and power.
Tier
a band of features in the build. We start a tier only when the one before it works.
Solver
the program that checks each token's path and says pass or fail, with the numbers. It follows fixed rules. No AI decides.
Contract
the agreed data format that every part of the project uses.
Folder
one person's own area of the project. Each person changes only their own folder.
Merge
putting everyone's work together on the main version.
Tag
a saved, known-good version that we can always demo from.
Go/no-go
a set time when we decide: start the next tier or not, or switch to the backup plan.
Jev
TypeSafe AI's typed-decision model. It turns a typed sentence into an edit and gives vote bubbles. It never decides pass or fail.

1. When: the tier ladder

Each tier starts only when the one before it is green. Diamonds are checkpoints and freezes; yellow triangles are switch times.

In plain words

  • Read it left to right. It is the clock, from 12:00 to 22:00.
  • The three boxes are the three tiers. Tier 1 must work: it is the demo we can always show. The features of each tier are in view 3.
  • Diamonds are fixed check times. At 17:00 we save tier 1 as "tier1-demo" and decide whether to start tier 2. At 19:30 we save "tier2-demo" and decide on tier 3.
  • Yellow triangles are backup decisions. For example, if the 3D view is not clear by 15:30, we switch to flat floor plans.
  • After 21:00 we only fix, write the README and run guide, rehearse, and record a backup video. Nobody adds new features.

2. How the parts connect

One folder per person. Arrows are what each folder hands to the next; data arrows carry contract/ types.

In plain words

  • Each solid box is one folder of the project, with the person who owns that folder. The dashed box is outside the repo: the Jev service and a plan B AI. View 3 says who owns each feature.
  • The app (P3) is the screen people click. It loads the building and asks the solver (P1) to check every token.
  • The solver answers pass or fail for each token, and says where and why it got stuck.
  • The viewer (P2) draws the 3D building and moves the tokens. Design (P4) gives the colours and icons.
  • P5 describes the building as data and works out the right answers by hand. The solver is tested against those answers.
  • jev/ (P1) uses Jev to turn a sentence such as "widen the plant shaft to 2 metres" into an edit. Only the solver decides pass or fail.
  • The bottom bar is the contract: the shared data format. Like a drawing or layer standard, everyone follows it, and only P1 changes it.

3. Who owns each feature

One row per feature, grouped by tier. One OWNER per row, or NO OWNER YET where the plan names nobody; "helps" marks the others the plan puts on it. Yellow letters point at what the team still has to decide.

In plain words

  • Read one row at a time. Each row is one feature of the game. The OWNER is the one person who makes sure it gets done.
  • "helps" means someone else also works on it, for example P5 works out the right answers for water by hand.
  • A yellow letter marks something to decide: the plan splits the feature between people, loads one person too much, or names no owner. The boxes under the table say what the plan says now and what we propose.
  • Nothing in the boxes is decided yet. The team decides together, then P1 updates docs/plan.md and AGENTS.md.

4. What the audience sees: the demo path

The 3-minute demo, beat by beat. Fix one, break another.

In plain words

  • This is the 3-minute demo story, left to right.
  • Each token shows PASS with a tick or FAIL with a cross.
  • Beat 2: the chiller is 1.6 m wide, but the plant shaft is only 1.2 m wide, so it gets stuck.
  • Beats 3 and 4: widening the shaft lets the chiller out, but the wider shaft cuts beam B2, so the structural load loses its support. Fix one, break another.
  • Beats 5 and 6: a transfer beam, a ramp and a wider lobby corner fix everything. Every token escapes.
